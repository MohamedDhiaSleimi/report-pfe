\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

This sprint report covers \textbf{Domain 3: Production Execution \& Traceability}.
Building upon the authentication and machine monitoring infrastructure established
in the previous sprints, this sprint delivers the core production execution
features: declaring production output, pausing and resuming operations, finishing
or cancelling orders, tracking production cycles over time, monitoring Bill of
Materials consumption, component barcode scanning, scrap declaration, supervisor
proxy declaration, and label printing. The result is a fully operational shop-floor
execution loop from order assignment through to order closure, material traceability,
and printed part identification.

	\midrule
	
	\businessrule{BR-EXEC-001}:  Single Running Operation per Machine & A machine may only have one operation in the \domainterm{Running} state at any given time. Before starting or resuming an operation, \texttt{EnsureNoRunningOperation()} queries all \techname{MES Operation Execution} records for the machine and verifies that none of their latest \techname{MES Operation Status} records has the status \domainterm{Running}. A violation triggers an error with the conflicting order and operation numbers included in the message. \\
	\midrule
	
	\businessrule{BR-EXEC-002}:  Declared Quantity Cannot Exceed Remaining Quantity & During \texttt{TryDeclareProduction()}, the sum of \texttt{TotalProducedQuantity} from the latest progression record and the new \texttt{input} is compared to \texttt{MESExecution."Order Quantity"}. If the sum exceeds the order quantity, an error is raised and no record is inserted. \\
	\midrule
	
	\businessrule{BR-EXEC-003}:  State Machine for Operation Status & Operation status transitions are strictly enforced:
	\begin{itemize}[noitemsep, topsep=0pt, partopsep=0pt, leftmargin=*]
		\item \domainterm{Running} $\rightarrow$ \domainterm{Paused} (via \texttt{TryPauseOperation}).
		\item \domainterm{Paused} $\rightarrow$ \domainterm{Running} (via \texttt{TryResumeOperation}).
		\item \domainterm{Running} or \domainterm{Paused} $\rightarrow$ \domainterm{Finished} or \domainterm{Cancelled} (via \texttt{TryCloseOperation}).
		\item \domainterm{Finished} or \domainterm{Cancelled} $\rightarrow$ any other state (blocked: \texttt{TryCloseOperation} raises an error).
	\end{itemize}
	Each transition inserts a new immutable \techname{MES Operation Status} record; no records are ever updated or deleted, providing a full audit trail. \\
	\midrule
	
	\businessrule{BR-EXEC-004}: Machine Status is Derived from Operation Status & \techname{MES Machine Status} records are inserted (never updated) whenever an operation transition occurs:
	\begin{itemize}[noitemsep, topsep=0pt, partopsep=0pt, leftmargin=*]
		\item Start / Resume $\rightarrow$ insert \domainterm{Working} status with the current production order number.
		\item Pause / Finish / Cancel $\rightarrow$ insert \domainterm{Idle} status with no production order.
	\end{itemize}
	The machine list display reads the most recent record for each machine (sorted by Last Updated At descending). \\
	\midrule
	
	\businessrule{BR-EXEC-005}:  Only Released Orders Can Be Started & \texttt{TryStartOperation()} filters Prod.\ Order Routing Line with \texttt{Status = Released}. Planned and Firm Planned lines are visible in the Flutter Orders tab but their Start Order button is disabled (\texttt{canStart = order.status == 'Released'}). \\
	\midrule

		\item Only users with the \userrole{Supervisor} role see the operator selector

		\item The selected operator's User Id is written to the \texttt{Declared By}

	\businessrule{BR-SCAN-001}: Internal Barcode Priority & 
	\begin{itemize}
		\item If a scanned DataMatrix string matches the proprietary pipe-separated
		      format, it is parsed locally without a server round-trip.
		\item External barcodes that do not match this format are resolved via
		      \apiendpoint{resolveBarcode()} using the \modulename{Item Identifier} table.
	\end{itemize} \\
	\midrule
	
	\businessrule{BR-SCAN-002}: Duplicate Scan Merging & 
	\begin{itemize}
		\item Scanning the same item twice increments the quantity on the existing row
		      in the pending scan list rather than adding a duplicate entry.
		\item The operator can adjust the quantity further using the +/$-$ controls
		      before confirming.
	\end{itemize} \\
	\midrule
	
	\multicolumn{2}{@{}l}{\textbf{Bill of Materials Rules}} \\
	\midrule
	
	\businessrule{BR-BOM-001}: Routing Link Code Scoping & When an order's components have Routing Link Codes assigned, \texttt{fetchBom()} uses the following three-condition filter to determine which components to show for a given operation:
	\begin{itemize}[noitemsep, topsep=0pt, partopsep=0pt, leftmargin=*]
		\item \textbf{Include}: components whose Routing Link Code matches the current operation's code (\texttt{belongsToThisOperation = true}).
		\item \textbf{Include}: components with an empty Routing Link Code when at least one component in the order has a routing link (shown as shared, \texttt{belongsToThisOperation = false}).
		\item \textbf{Exclude}: components whose Routing Link Code is non-empty and differs from the current operation's code (they belong to a different operation).
	\end{itemize}
	When no component in the order has a Routing Link Code, all components are shown as operation-specific. \\

	\midrule

No update or delete operations are performed on these tables outside of testing pages, ensuring a complete chronological audit trail for every machine, order, and operator action. \\
	\midrule
	
	\businessrule{BR-TRACE-002}: Operator Identity on Every Record & All progression, status, and consumption records stamp the \texttt{Operator Id} using the BC session \texttt{UserId} at insert time. The \texttt{fetchProductionCycles()} endpoint resolves first and last name from the \techname{Employee} table for display. \\

\section{Design}

\subsection{Use Case Diagram}

\noindent
\vspace{0pt}
This sprint adds production execution actors and interactions centred on the \userrole{Operator} and \userrole{Supervisor} roles. The primary use cases are: Declare Production, Pause Operation, Resume Operation, Finish Operation, Cancel Operation, View BOM Components, View Operation Detail, View Machine History, and Change Password.

The \userrole{Supervisor} role is a superset of \userrole{Operator}: both roles can declare production, pause, resume, and view detail; only the Supervisor may close (finish or cancel) a production order in the intended business flow, although the current implementation enforces this at the UI layer through the \texttt{canCloseProductionOrder} flag rather than at the API level. 	\item A \domainterm{Finished} or \domainterm{Cancelled} status record is inserted.
	\item The execution end time is stamped.
	\item An Idle machine status record is inserted.
	\item The user is navigated back to the machine page.
	\end{itemize} \\
	\midrule
	\textbf{Main Scenario} & 
	\begin{enumerate}[noitemsep, topsep=0pt, partopsep=0pt, leftmargin=*]
	\item The user taps \uilabel{Finish Production Order} (if complete) or \uilabel{Cancel Production Order} (if incomplete).
	\item A confirmation dialog is displayed; the user confirms.
	\item The system POSTs to \apiendpoint{/MESWebService\_finishOperation} or \apiendpoint{cancelOperation}.
	\item The ERP validates, inserts the status record, stamps the end time, and inserts an Idle machine status.
	\item Flutter calls \texttt{Navigator.pop()} to return to the machine page.
	\end{enumerate} \\
\end{longtable}

\subsection{Class Diagram}

The UML Class Diagram (Figure~\ref{fig:s3-class-diagram-s3}) extends the Sprint~2
domain model with three new tables. \modulename{MES Operation Execution} (50110)
is the central anchor record linking a machine, production order, and operation
to its full lifecycle; it holds item description, order quantity, and start/end
timestamps. \modulename{MES Operation Progression} (50109) is an append-only
table of production cycle declarations, each referencing an execution and
accumulating \texttt{TotalProducedQuantity} from the previous cycle.
\modulename{MES Component Consumption} (50111) records scrap and barcode scan
events, also referencing an execution. Both progression and consumption records
are child tables of the execution record, forming a hub-and-spoke traceability
model.

\subsection{Frontend Implementation}

This sprint introduces a key reactive pattern: a shared \texttt{StreamController<void>.broadcast()} in \techname{MachineordersProvider} and \techname{MesComponentConsumptionProvider}. When any write action (declare, pause, resume, finish, cancel) succeeds, \texttt{triggerRefresh()} adds an event to the controller. All live data streams (\texttt{fetchOperationLiveDataStream}, \texttt{streamProductionCycles}, \texttt{streamBom}) are implemented as \texttt{async*} generators that yield on both the initial fetch and on each event from the shared broadcast stream, enabling coordinated, push-driven UI updates without polling.

\subsubsection{User Interface}
Figures~\ref{fig:s3-ui-op-detail-running} through~\ref{fig:s3-ui-op-detail-cancelled} illustrate the \uilabel{Operation Detail Page} across its four possible states: Running, Paused, Finished, and Cancelled. Each view adapts its action buttons and status badge to the current state, while the production chart, cycle table, and BOM list remain consistently visible. On desktop, the page uses a two-column layout with order information and production data on the left, and the \uilabel{Quick Actions} panel on the right; on mobile, these sections stack vertically. Action button availability is state-dependent: \uilabel{Declare Production} and \uilabel{Report Reject} are disabled in the Paused, Finished, and Cancelled states; the close button triggers a \uilabel{Finish Production Order} or \uilabel{Cancel Production Order} action depending on whether the progress has reached 100\%; and \uilabel{Print Label} is enabled only once the operation is finished.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

This sprint delivered the complete shop-floor execution loop for the MES system.
Operators can now start, pause, resume, and close production operations, declare
production output cycle by cycle, track cumulative progress through real-time
charts and paginated tables, inspect the Bill of Materials, scan physical components
via DataMatrix barcodes, declare scrapped units with reason codes, and print
traceable labels for both production orders and individual declared units.
Supervisors gain the ability to declare production on behalf of a specific operator,
with a full attribution audit trail. The reactive stream architecture ensures that
all UI panels update in concert after every write action, providing a consistent
and accurate view of the production floor without manual refreshes.
