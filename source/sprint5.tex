\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

This sprint delivers the conversational intelligence layer of the \domainterm{MES}
solution. Building upon the production execution and administration infrastructure
established in the previous sprints, this sprint introduces an embedded
natural-language chat assistant that allows operators and supervisors to query
machine status, production progress, scrap data, Bill of Materials, and operation
history without navigating the full interface. The assistant resolves ambiguous
machine references, answers fleet-wide questions through parallel fan-out queries,
proactively surfaces operational anomalies, and provides contextual navigation
shortcuts directly within the chat reply.

The implementation spans three new components: a \techname{Node.js} reverse-proxy
middleware layer that handles \domainterm{SSPI/Windows} authentication toward
\techname{Business Central} and routes AI chat traffic to a dedicated
\techname{Python} agent; the \techname{Python FastAPI} AI agent itself, which
classifies user intent, executes tool chains against the existing BC web services,
enriches results with pure-Python analytics, and synthesises natural-language
replies using a configurable multi-provider \domainterm{LLM} client; and the
\techname{Flutter} chat UI, integrated directly into the machine list page as a
side panel or dialog.

\section{Implementation}

\subsection{Node.js Middleware}
\subsubsection{Overview}

The \techname{Node.js} middleware (\texttt{node-middleware/}) is an
\techname{Express~5} application that acts as the single network bridge between
the \techname{Flutter} client and \techname{Business Central}.

The middleware exposes two distinct route families: \texttt{/api/<endpoint>}
(proxied to BC) and \texttt{/api/ai/*} (forwarded to the Python agent).

\subsubsection{AI Proxy Layer}

The \texttt{src/aiProxy.js} \techname{Express} Router, mounted at
\texttt{/api/ai}, forwards \texttt{POST /chat} requests to the Python agent at
\texttt{AI\_AGENT\_URL/chat} using the native \texttt{fetch} API. It validates
that both \texttt{message} and \texttt{user\_context} are present before
forwarding, enforces a \texttt{AI\_TIMEOUT\_MS} abort timeout, and passes the
Python agent's response through unchanged. A \texttt{GET /api/ai/health}
endpoint aggregates the Node process uptime with the Python agent's own health
status for monitoring purposes.

\subsection{Python AI Agent}
The agent makes exactly two \domainterm{LLM} calls per user message .
\textbf{Call 1 --- Intent classification.} The \modulename{LLMIntentIdentifier}
sends the user message, role, and work centres to the LLM with a structured
system prompt listing all 17 available tools and their required arguments. The
LLM responds with a JSON plan containing the intent label, a list of
\modulename{ToolStep} objects (each with a tool name, arguments — which may be
slot references to previous steps — and a result key), and a reasoning string.
The plan is validated against the tool catalogue before being converted to a
\modulename{ToolChain} dataclass. If the LLM call fails for any reason, the
deterministic regex classifier in \texttt{agent/intent.py} is used as a fallback.
The entire classification reasoning is stored in a \modulename{ThinkingBlock} and
returned in \texttt{ChatResponse.thinking} for debugging; it is never shown to the
user.

\textbf{Call 2 --- Synthesis.} After all tool steps have been executed and their
results enriched, the \texttt{Orchestrator.\_synthesise()} method builds a context
block containing the enriched data in markdown format (truncated at
\texttt{LLM\_MAX\_CONTEXT\_CHARS} characters) and calls the LLM with the
\texttt{SYNTHESIS\_SYSTEM} and \texttt{SYNTHESIS\_USER\_TEMPLATE} prompts. The
system prompt instructs the model to answer only from the pre-fetched data, to
highlight anomalies prominently, to respond in the same language as the user, and
to optionally append a \texttt{actions} JSON block containing up to 4
\modulename{RedirectAction} objects.

\subsubsection{Intent Classification}

\textbf{LLM classifier.} The \modulename{LLMIntentIdentifier} constructs a
system prompt containing the full \texttt{TOOL\_CATALOGUE}
 and the list of valid intent labels. The user
message is injected via \texttt{\_IDENTIFIER\_USER\_TEMPLATE} along with the
user's role and work centres. The raw LLM response is stripped of JSON fences,
parsed, validated against \texttt{\_VALID\_TOOLS} and \texttt{\_INTENT\_MAP}, and
converted to a \modulename{ToolChain} via \texttt{\_plan\_to\_tool\_chain()}.

\textbf{Scrap spike detection.} The \texttt{analyse\_scrap()} function computes
the scrap rate for the most recent quarter of declared cycles and compares it to
the rate for the earlier three-quarters. If the recent rate exceeds the baseline
by a factor of 2.5 or is above the critical threshold of 15\%, a spike is flagged
and explicitly mentioned in the synthesis prompt.

\textbf{Velocity projection.} The \texttt{analyse\_velocity()} function derives
the actual production rate (units per hour) from the last 6 declared cycles and
compares it to the required rate (remaining quantity divided by time until the
planned end). The result is one of \textit{ahead}, \textit{on\_pace}, or
\textit{behind}, along with a projected completion timestamp.

\subsection{Flutter Frontend}

\subsubsection{Chat Page and Provider}

The \techname{AiChatPage} widget adapts its rendering to the available screen
width: on screens wider than 600\,dp it is displayed as a \texttt{Positioned}
overlay panel (400\,dp wide, full height) anchored to the right side of the
\techname{MachineListPage}; on mobile it opens as a \texttt{Dialog}. The chat
input field and conversation history list are shared between both modes.

The \techname{AiChatProvider} maintains the in-session conversation history as a
\texttt{List<ConversationTurn>}. On each \texttt{sendMessage()} call it appends
the user turn, calls \texttt{AiChatService.sendMessage()} with the history
(excluding the most recently appended turn, which the server receives as the
primary message), appends the assistant reply, and stores the last
\techname{AiChatResponse} for action button rendering.

\subsubsection{Redirect Actions}

After each assistant reply, the \techname{AiChatPage} inspects
\texttt{lastResponse.actions}. If non-empty and the message is the last in the
conversation, up to 4 \techname{ElevatedButton} widgets are rendered below the
reply bubble. The \texttt{\_handleAction()} method routes each action type:

\begin{itemize}[noitemsep]
	\item \texttt{redirect\_machine} $\to$ \texttt{Navigator.push} to
	      \techname{MachineMainPage} with the payload \texttt{machineNo}.
	\item \texttt{redirect\_operation} $\to$ \texttt{Navigator.push} to
	      \techname{OperationDetailPage} with \texttt{machineNo},
	      \texttt{prodOrderNo}, and \texttt{operationNo}.
	\item \texttt{redirect\_machine\_list} $\to$ \texttt{Navigator.popUntil}
	      to the root route (machine list).
	\item \texttt{redirect\_machine\_dashboard} $\to$ \texttt{Navigator.push}
	      to the admin machine dashboard.
	\item \texttt{redirect\_history} $\to$ \texttt{Navigator.push} to
	      \techname{MachineHistoryPage} with \texttt{machineNo}.
\end{itemize}

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

This sprint delivered the conversational intelligence layer of the \domainterm{MES}
solution.

The AI agent implements a two-\domainterm{LLM}-call pipeline: a first call
classifies user intent and produces an executable \modulename{ToolChain} plan
, and a second call
synthesises the final natural-language reply from the enriched tool results.
Pure-Python analytics (deadline enrichment, scrap spike detection, velocity
projection) pre-compute key facts so the synthesis \domainterm{LLM} receives
answers rather than raw numbers.

Operators and supervisors can now ask questions in natural language, receive
machine and production data scoped strictly to their work centres, navigate
directly to relevant screens via action buttons embedded in the reply, and obtain
proactive alerts for overdue orders, scrap anomalies, and paused operations —
all without leaving the chat interface.
