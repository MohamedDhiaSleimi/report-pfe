\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

This sprint delivers the conversational intelligence layer of the \domainterm{MES}
solution. Building upon the production execution and administration infrastructure
established in the previous sprints, this sprint introduces an embedded
natural-language chat assistant that allows operators and supervisors to query
machine status, production progress, scrap data, Bill of Materials, and operation
history without navigating the full interface. The assistant resolves ambiguous
machine references, answers fleet-wide questions through parallel fan-out queries,
proactively surfaces operational anomalies, and provides contextual navigation
shortcuts directly within the chat reply.

\section{Implementation}

\subsection{Node.js Middleware}
\subsubsection*{Overview}

The \techname{Node.js} middleware (\techname{node-middleware/}) is an
\techname{Express~5} application that acts as the single network bridge between
the \techname{Flutter} client and \techname{Business Central}.

The middleware exposes two distinct route families: \techname{/api/<endpoint>}
(proxied to BC) and \techname{/api/ai/*} (forwarded to the Python agent).

\subsubsection*{AI Proxy Layer}

The \techname{src/aiProxy.js} \techname{Express} Router, mounted at
\techname{/api/ai}, forwards \techname{POST /chat} requests to the Python agent at
\techname{AI\_AGENT\_URL/chat} using the native \techname{fetch} API. It validates
that both \techname{message} and \techname{user\_context} are present before
forwarding, enforces a \techname{AI\_TIMEOUT\_MS} abort timeout, and passes the
Python agent's response through unchanged. A \techname{GET /api/ai/health}
endpoint aggregates the Node process uptime with the Python agent's own health
status for monitoring purposes.

\subsection{Python AI Agent}	
Figure~\ref{fig:s5-architecture} shows the file architecture of the AI assistant layer.
The agent makes up to three \domainterm{LLM} calls per user message;
one or two calls for intent classification (a second call is triggered
automatically if the first response is malformed), and one call for synthesis.


\noindent
\begin{minipage}[t]{0.6\textwidth}
	\vspace{0pt}

	\textbf{Call 1 --- Intent classification.} The \modulename{LLMIntentIdentifier}
	following a ReAct-style reasoning pattern,
	sends the user message, role, and work centres to the LLM with a structured
	system prompt listing all 17 available tools and their required arguments. The
	LLM responds with a JSON plan containing the intent label, a list of
	\modulename{ToolStep} objects (each with a tool name, arguments which may be
	slot references to previous steps and a result key), and a reasoning string.
	The plan is validated against the tool catalogue before being converted to a
	\modulename{ToolChain} dataclass.
	The entire classification reasoning is stored in a \modulename{ThinkingBlock} and
	returned in \techname{ChatResponse.thinking} for debugging; it is never shown to the
	user.

	\textbf{Call 2 --- Synthesis.} After all tool steps have been executed and their
	results enriched, the \techname{Orchestrator.\_synthesise()} method builds a context
	block containing the enriched data in markdown format (truncated at
	\techname{LLM\_MAX\_CONTEXT\_CHARS} characters) and calls the LLM with the
	\techname{SYNTHESIS\_SYSTEM} and \techname{SYNTHESIS\_USER\_TEMPLATE} prompts. The
	system prompt instructs the model to answer only from the pre-fetched data, to
	highlight anomalies prominently, to respond in the same language as the user, and
	to optionally append a \techname{actions} JSON block containing up to 4
	\modulename{RedirectAction} objects.

The user message is injected 
via \techname{\_IDENTIFIER\_USER\_TEMPLATE} along with the

If the first attempt fails (timeout, malformed JSON, or invalid tool names),
the identifier automatically retries with a second \domainterm{LLM} call
that injects the original error reason into the conversation so the model
can self-correct. Only after both attempts fail does the identifier return
a \techname{general} intent with an empty tool chain.

\subsubsection*{Machine Name Resolution}
When a user references a machine by a non-canonical name or a fuzzy
identifier (e.g.\ ''Fraiseuse 3'', ''milling machine'', ''mc 1''),
the orchestrator invokes the \techname{agent/resolver.py} module before
executing the tool chain. The resolver applies a five-tier cascade
against the full machine catalogue fetched from \techname{Business Central}:

\begin{enumerate}[noitemsep, topsep=4pt, leftmargin=*]
	\item \textbf{Exact canonical match} --- the query matches a
	\techname{machineNo} character-for-character (confidence 1.0).
	\item \textbf{Normalised exact match} --- accents stripped,
	case-folded, and punctuation normalised before comparison
	(confidence 0.97).
	\item \textbf{Digit-suffix match} --- the numeric suffix of the query
	matches the machine's numeric suffix after stripping leading zeros
	(confidence 0.88--0.90).
	\item \textbf{Token-overlap score} --- query tokens are matched against
	the machine name using a containment-biased formula; short
	queries that are fully contained in a longer name (e.g.
	Presse'' $\subset$ Presse hydraulique'') score  $\geq$ 0.80,
	\item \textbf{Edit\-distance (Levenshtein)} --- normalised similarity
	against the machine ID, used as a typo\-recovery fallback.
\end{enumerate}
A match at or above \techname{HIGH\_CONFIDENCE} (0.85) is accepted
silently. A match between \techname{MIN\_CONFIDENCE} (0.45) and
\techname{HIGH\_CONFIDENCE} is accepted but the assumption is surfaced
in the \domainterm{LLM} context block. A match below
\techname{MIN\_CONFIDENCE} is treated as ambiguous: the agent returns
a clarification message listing up to three candidates with their
work-centre and status, without making any tool calls.

\textbf{Scrap spike detection.} The \techname{analyse\_scrap()} function computes
the scrap rate for the most recent quarter of declared cycles and compares it to
the rate for the earlier three-quarters. If the recent rate exceeds the baseline
by a factor of 2.5 or is above the critical threshold of 15\%, a spike is flagged
and explicitly mentioned in the synthesis prompt.

\textbf{Velocity projection.} The \techname{analyse\_velocity()} function derives
the actual production rate (units per hour) from the last 6 declared cycles and
compares it to the required rate (remaining quantity divided by time until the
planned end). The result is one of \textit{ahead}, \textit{on\_pace}, or
\textit{behind}, along with a projected completion timestamp.

\subsubsection*{Context Serialisation and Budget Management}
Before the synthesis \domainterm{LLM} call, \techname{Orchestrator.\_build\_context()}
converts the enriched result dictionary into a single markdown string that
fits within the \techname{LLM\_MAX\_CONTEXT\_CHARS} character budget
(configurable via environment variable, default 20,000 characters).
Each result key is rendered by \techname{\_compress\_section()}, which
dispatches to one of 18 type-specific format helpers. Instead of passing
raw JSON to the \domainterm{LLM}, every helper produces the most
token-efficient representation for its data type:
\begin{itemize}[noitemsep, topsep=4pt, leftmargin=*]
  \item \textbf{Tabular data} (machines, orders, history, cycles, BOM,
        dashboard, operators, work centres, delays, production orders,
        activity log, consumption) → compact markdown tables via
        \techname{\_md\_table()}, with cell content capped at 38 characters
        and row counts capped per key (e.g.\ 20 rows for orders, 30 for
        cycles).
  \item \textbf{Scalar / KPI data} (live operation data, scrap summary,
        supervisor overview, personal data)→ key-value bullet lists
        with pre-computed analysis interpretations inline.
  \item \textbf{Pre-computed interpretation strings} (produced by the
        enrichment functions in \techname{data\_analysis.py}) are always
        rendered first in each section in bold, so the \domainterm{LLM}
        receives the conclusion before the supporting data.
\end{itemize}
Sections are added in order until the character budget is reached.
If a section would overflow the budget, \techname{\_emergency\_compress()}
is called first: it emits only the pre-computed interpretation string
for that key, appending \textit{(detail omitted --- budget)}. If even
the interpretation string does not fit, the section is silently skipped.
This guarantees the \domainterm{LLM} always receives a coherent, complete
context rather than a truncated JSON fragment.

\subsection{Flutter Frontend}

\subsubsection*{Chat Page and Provider}

The \techname{AiChatPage} widget adapts its rendering to the available screen
width: on screens wider than 600\,dp it is displayed as a \techname{Positioned}
overlay panel (400\,dp wide, full height) anchored to the right side of the
\techname{MachineListPage}; on mobile it opens as a \techname{Dialog}. The chat
input field and conversation history list are shared between both modes.

The \techname{AiChatProvider} maintains the in-session conversation history as a
\techname{List<ConversationTurn>}. On each \techname{sendMessage()} call it appends
the user turn, calls \techname{AiChatService.sendMessage()} with the history
(excluding the most recently appended turn, which the server receives as the
primary message), appends the assistant reply, and stores the last
\techname{AiChatResponse} for action button rendering.

\subsubsection*{Redirect Actions}

After each assistant reply, the \techname{AiChatPage} inspects
\techname{lastResponse.actions}. If non-empty and the message is the last in the
conversation, up to 4 \techname{ElevatedButton} widgets are rendered below the
reply bubble. The \techname{\_handleAction()} method routes each action type:

\begin{itemize}[noitemsep]
	\item \techname{redirect\_machine} $\to$ \techname{Navigator.push} to
	      \techname{MachineMainPage} with the payload \techname{machineNo}.
	\item \techname{redirect\_operation} $\to$ \techname{Navigator.push} to
	      \techname{OperationDetailPage} with \techname{machineNo},
	      \techname{prodOrderNo}, and \techname{operationNo}.
	\item \techname{redirect\_machine\_list} $\to$ \techname{Navigator.popUntil}
	      to the root route (machine list).
	\item \techname{redirect\_machine\_dashboard} $\to$ \techname{Navigator.push}
	      to the admin machine dashboard.
	\item \techname{redirect\_history} $\to$ \techname{Navigator.push} to
	      \techname{MachineHistoryPage} with \techname{machineNo}.
\end{itemize}

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

This sprint delivered the conversational intelligence layer of the \domainterm{MES}
solution.

The AI agent implements a two-\domainterm{LLM}-call pipeline: a first call
classifies user intent and produces an executable \modulename{ToolChain} plan
, and a second call
synthesises the final natural-language reply from the enriched tool results.
Pure-Python analytics (deadline enrichment, scrap spike detection, velocity
projection) pre-compute key facts so the synthesis \domainterm{LLM} receives
answers rather than raw numbers.

Operators and supervisors can now ask questions in natural language, receive
machine and production data scoped strictly to their work centres, navigate
directly to relevant screens via action buttons embedded in the reply, and obtain
proactive alerts for overdue orders, scrap anomalies, and paused operations
all without leaving the chat interface.
